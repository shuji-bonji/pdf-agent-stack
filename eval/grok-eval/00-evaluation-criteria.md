# 00 — 評価の見方

利用価値があるかと、直す箇所があるかを、同じ物差しで書きます。

## 判定しないもの

モデルの文章の上手さだけでは採点しません。次を見ます。

1. 正しいサーバーを呼んだか
2. 呼び出し順が Skill の型に沿ったか
3. ツールの JSON を、禁止された言い回しに翻訳しなかったか
4. 失敗を「成功」に書き換えなかったか
5. 人が次に取る行動が報告書から分かるか

## 利用価値の 4 段階

各ユースケースの最後に、次のどれかを 1 つ付けます。理由はツール応答を引用して書いてください。

| 段階 | 意味 |
| --- | --- |
| 実務で使える | 指示どおりの入力で、判定とレポートが揃い、人が判断できる |
| 条件付きで使える | 動くが、ホスト設定・フォント・veraPDF・コーパスのどれかが無いと欠ける |
| デモには足りる | スモークは通るが、実務データや失敗経路で型が崩れる |
| 使えない | 起動しない、責務を跨ぐ、判定をモデルが上書きする |

## 改善点の分類

| 種別 | 書く対象 |
| --- | --- |
| MCP の応答 | エラーコードが無い、JSON の形が版で違う、入力スキーマが分かりにくい |
| Skill の編成 | 呼ぶ順をモデルが外す、Report の必須欄が落ちる |
| ホスト適合 | Grok Build が MCP instructions を読まない、Skill を発見しない |
| 文書 | サイトのプロンプト例では足りない、絶対パス必須が分からない |
| 検体 | 実務データで初めて出る欠陥 |

## 風合い（質感）の記録

数値化できないが再現したい観察です。次の語で書いてください。印象語だけで終わらせないでください。

- 最初のプロンプトから、何手で目的のツールに着いたか
- モデルが reader の観測を判定に伸ばしたか（伸ばした文を引用）
- `ensure_pdfa` の warning を無視したか
- 同じ依頼を 2 回出したとき、`evaluate_policy` の `verdict` が一致したか
- エラー `FONT_REQUIRED` / `ENCRYPTED_PDF` / `SIGNED_PDF` の `next_actions` に従ったか
- Trust Report / Publish Report / Read Report の見出しがサイトの型と一致したか

## 想定と実際の表

各ステップは必ず 4 列にします。

| ステップ | 入力（ツール名と主パラメータ） | 想定 | 実際 |
| --- | --- | --- | --- |
| 例 | `evaluate_policy` profile=`government` | `verdict` が 4 値のいずれか。`firedRules` がある | （実測の verdict と ruleId） |

想定を「成功する」とだけ書かないでください。返るフィールド名を書いてください。

## 横断で見る境界違反

1 件でも次があれば、そのユースケースは「使えない」側に寄せます。

- pdf-spec が検証対象 PDF を開こうとした
- pdf-reader の出力だけを根拠に「改ざんされていない」と書いた
- pdf-writer が署名した、と書いた（writer は署名しない）
- `evaluate_policy` を呼ばずに Trust Report の判定欄を埋めた
- PDF/A を「ISO 19005 準拠」と書いた
- 検査未実施を `passed` と書いた
